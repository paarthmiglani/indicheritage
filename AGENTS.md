## Agent Instructions for Cultural Artifact Explorer

Welcome, Agent! This file provides guidelines for working on the Cultural Artifact Explorer & Multimodal Retrieval System.

### Project Overview

This project aims to build a system for exploring cultural artifacts. Key components include OCR for text extraction from images, NLP for text understanding and translation, and multimodal retrieval (image-text).

### Development Guidelines

1.  **Modularity**: Keep components (OCR, NLP, Retrieval, UI) as modular as possible. Each main directory (`ocr/`, `nlp/`, `retrieval/`) should be self-contained in its core logic.
2.  **Configuration**: For model paths, API keys (if any in the future), and other configurable parameters, consider using configuration files (e.g., YAML or JSON) or environment variables. Avoid hardcoding these directly into scripts, especially for sensitive information. We have a `training_configs/` directory; similar approaches can be used for application configurations if needed.
3.  **Dependencies**: Maintain a `requirements.txt` file (to be added) for Python dependencies. When adding new libraries, update this file.
4.  **Logging**: Use the `utils/logging.py` module for standardized logging across the project once it's more developed. For now, print statements are fine for placeholder scripts.
5.  **Testing**: The `tests/` directory is designated for unit and integration tests. As functionalities are implemented, corresponding tests should be added. Aim for good test coverage.
6.  **Offline First (for OCR/NLP models)**: The user has specified a preference for offline test/tuning. This means that for core OCR and NLP model functionalities, prioritize solutions that can download models and run them locally, rather than relying on cloud-based APIs, unless explicitly stated otherwise for a specific task.
7.  **Indic Languages Focus**: The project mentions "Indic OCR" and "IndicTrans2". Keep this focus in mind when selecting models and libraries.
8.  **Python Version**: Assume Python 3.8+ unless specified otherwise.
9.  **Code Style**: Follow PEP 8 guidelines for Python code. Use linters and formatters like Black or Flake8 if possible (though not set up yet).
10. **Commit Messages**: Write clear and concise commit messages. A good format is a short subject line (max 50 chars), a blank line, and then a more detailed explanation if needed.
11. **Branching**: Use feature branches for new functionalities or significant changes. For example, `feature/ocr-integration` or `bugfix/nlp-translation-error`.

### Specific Module Notes

*   **`ocr/`**: Focus on models that can be run offline. While Indic-DOCTR was mentioned, if it proves difficult to set up for offline use without user intervention, research alternatives that are easier to manage in an agent-driven setup.
*   **`nlp/`**: Similarly, for translation (IndicTrans2), summarization (mBART), and NER (IndicBERT/XLM-R), prioritize models that can be downloaded and run locally.
*   **`retrieval/`**: FAISS or Annoy are good choices for local nearest neighbor search. Embeddings should be generated by models like BLIP or CLIP that can also be run locally.
*   **`interface/app.py`**: The current placeholder is for Streamlit. If you are asked to develop the UI, confirm if Streamlit is still the choice. Remember to manage dependencies like Pillow if you add image manipulation directly in the UI code.

### Communication

*   If instructions are unclear, ask for clarification.
*   Provide updates on your plan and progress.
*   If you encounter significant roadblocks, explain the issue and your attempted solutions.

By following these guidelines, we can build a robust and maintainable system. Happy coding!
